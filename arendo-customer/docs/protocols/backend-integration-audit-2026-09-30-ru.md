# Аудит черновика backend-протокола — 30.09.2026

Статус: **предварительный аудит совместимости спецификации с текущей Android APK**. Это не
подтверждение, что все описанные функции уже реализованы сервером или устройством.

## Что в серверном проекте описано правильно

- постоянный WebSocket over TLS с токеном устройства в handshake-заголовке, без токена в URL;
- `postamatId`, `cellCode`, уникальные ID операций, heartbeat и идентификатор сессии;
- срок действия команды и дедупликация, отдельное различение состояния двери и замка;
- запрет неожиданного исполнения просроченной команды после восстановления связи;
- модульная телеметрия и журналируемые события как отдельные бизнес-функции.

Это качественные требования к серверу, но документ сам по себе не доказывает, что они включены в
тестовый сервер.

## Блокирующие расхождения с текущей APK

| Тема | Черновик backend | Текущая APK | Что согласовать/исправить |
|---|---|---|---|
| Конверт команды | Поля команды находятся внутри `command: { ... }` | Обработчик сейчас читает `id`, `kind`, `postamatId` и `payload` на верхнем уровне сообщения `type="command"` | Выбрать одну точную JSON-форму или адаптировать APK; прислать golden JSON для теста |
| `sessionId` | Сервер выдаёт и ожидает `sessionId` в последующих сообщениях | APK пока не сохраняет его из `welcome` и не добавляет в ACK/event | Добавить поддержку на устройстве и проверку на сервере либо сделать поле необязательным в v1 |
| ACK и открытие | В проекте нужно различать принятие операции и подтверждение двери датчиком | APK ACK после выполнения 2-секундного импульса означает `open_command_accepted`; физическое открытие подтверждается отдельным входным событием | Сервер не должен считать ACK импульса подтверждением открытой двери/оплаты; описать стадии и JSON-ответы |
| Тайм-аут обратной связи | В материалах обсуждалось ожидание до 30 секунд; в черновике также есть более короткое ожидание ACK | 30-секундный device-side timeout после открытия ещё не реализован; человек может открыть дверцу позже | Разделить транспортный ACK и ожидание факта двери; определить тайм-аут и позднее событие без ложного успеха |
| Поддержанные команды | Черновик включает дополнительные команды/медиа и обслуживание | В текущем обработчике поддержаны `open_cell` и `cell_report`; неизвестные команды отклоняются | Пометить остальные команды `planned/unsupported`; не отправлять их в текущую APK |
| Поля событий/времени | В черновике предусмотрены поля сессии и времени | APK отправляет `occurredAt`, `eventId`, `detail.source` и `detail.simulated`; схема времени разбирает только секунды UTC с суффиксом `Z` | Зафиксировать названия, формат RFC 3339 и обязательность каждого поля; проверить дробные секунды/смещения |
| `hello`/heartbeat | Черновик описывает `keyVersion`/модули/сетевую телеметрию | APK передаёт базовые `cells`, `capabilities`, `net.kind`; некоторые поля draft не формируются | Указать `required` и `optional`, версию схемы и поведение для отсутствующих/неизвестных полей |
| Door state | Сервер должен показывать достоверное состояние | Четырёхканальный demo input трактуется по стендовой логике; события помечены `simulated:true`; D05–D10 без входа остаются `unknown` | Не показывать simulator-события как подтверждение реальной двери; дождаться проверки контакта конкретного замка |

## Минимальный контракт для первого сквозного испытания

1. Сервер подключается по `wss://.../v1/device/socket` и аутентифицирует устройство заголовком
   `X-Device-Token`. Токены, SMS-коды и секреты не включать в Git, логи или примеры.
2. Стороны согласуют один точный вариант `hello → welcome → heartbeat`, с обязательными полями и
   правилами `sessionId`.
3. Сервер выдаёт только `open_cell` с уникальным `id`, правильными `postamatId`, `cellCode` и
   коротким `expiresAt`; команда не ставится в очередь на исполнение после истечения срока.
4. ACK `open_command_accepted` означает только принятие/выполнение импульса управления. Только
   отдельное достоверное событие датчика может изменить дверь на `open` или `closed`.
5. `cell_report` и heartbeat не заменяют журнал физических переходов; сервер сохраняет события по
   `eventId` без дублирования и показывает время/источник/признак тестовой симуляции.
6. На разрыв связи тестируются просроченная команда, повтор команды, поздний feedback и
   восстановление WebSocket. Никакая старая команда открытия не выполняется после reconnect.

Backend использует только бизнес-идентификаторы `postamatId` и `cellCode` — не номера Modbus slave,
не X/Y, не USB-порт и не скорость линии.

## Вопросы к backend-разработчику

- Какова окончательная структура одного сообщения `command`: вложенная или плоская? Предоставьте
  JSON для команды и все ответы с точными типами полей.
- Сервер уже выдаёт `sessionId`? Обязан ли каждый ACK/event повторять его?
- Какие стадии команды сохраняются и отображаются: `received`, `accepted`, `door_opened`, timeout,
  failed? Какое действие выполняется при пропаже сети в каждом интервале?
- Какой формат `expiresAt` принят (UTC RFC 3339), и какой допустимый clock skew?
- Какие команды и capabilities реально включены в тестовый сервер сейчас, а какие остаются в
  roadmap?
- Где оператор видит connection state, последнюю heartbeat, состояние D01–D28 и журнал событий?
- Утвердите имя временного `postamatId`: `map-7` в лабораторных примерах — тестовая идентичность,
  не производственный номер.

До согласования JSON-схемы документ backend и APK следует считать **не полностью совместимыми**.
